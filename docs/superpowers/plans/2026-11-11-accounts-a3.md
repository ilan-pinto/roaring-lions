# Accounts A3: versus records and the profile (plan, GH-1075)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A versus match that a member plays is recorded on the member's account, but only a result the server can
stand behind. The profile shows the member's history and W-L. The lobby and the match show members, guests and bots as
spec §5.3 says. The lead can blank a display name from `/stats`.

**Architecture:** The seat's member comes from the session cookie, read by the Worker's `/api/match` create and join
routes, never from the body. The Worker hands the member to the MatchRoom in the Worker-to-room request, and the room
keeps it in its meta. The seat ticket is unchanged. `over` gains the result each seat's sim reached
(`over{tick, result}`, the matchmaking spec's P0 rule, which has not landed). A pure rule in `room-core.ts` turns an ended
room into a record draft or nothing. The room writes the draft to the accounts database in one batch when the room
ends. Member labels go in the lobby message only, never in `MatchConfig`, so a public id or display name never reaches
the desync log, a replay or a feedback report. The app shows the labels in the lobby and carries them into the match
HUD. The profile reads the new `GET /api/account/matches`. A bot seat carries the model its operator declared (a listed
id or "Other" plus a typed name), a label only, stored in `match_seat.bot_label`. **No migration:** `0001_members.sql`
already holds `match_record` and `match_seat` (its `bot_label` column included), and A1 already built their export,
delete and orphan sweep.

**Tech Stack:** TypeScript strict, Cloudflare Workers and Durable Objects, D1 (`node:sqlite` in tests through
`test-d1.ts`), vitest, jsdom.

**Spec:** `docs/superpowers/specs/2026-11-07-accounts-profiles-design.md` §5 (all of it), §6.1, §6.3, §6.4 step 3 and
§7 (A3, tests A3-1 to A3-8). Read it with the A0/A1 plan (`2026-11-08-accounts-a0-a1.md`) and the A2 plan
(`2026-11-09-accounts-a2.md`). Their §0 rulings bind this plan where they touch it. Also read the matchmaking spec
`2026-10-28-public-matchmaking-design.md` §1.3 and its P0 table: A3 builds P0's agreed-result rule for the accounts
database, and nothing else of P0.

**Lead rulings that bind this plan (GH-1075):**
- 7 Nov: L10 (telemetry never linked to a member), L11 (a member's name is shown; their W-L is hidden until "Show my
  record" is on), versus pays 0 coins.
- 8 Nov: the switch opens after A1, so the privacy text for what a phase stores ships with that phase. Opus reviews the
  security tasks and Sonnet implements.
- 9 Nov: the A2 precedents (the privacy update ships with the phase, no lead step when there is no migration).
- 11 Nov, on this plan (GH-1075, "Lead rulings on the accounts A3 plan (PR 1250)"): (1) W-L counts every agreed result,
  guests and bots included, the two-tab risk accepted; (2) a bot seat's operator declares its model, from a list or
  "Other" plus a typed name, stored with the seat and shown in history and the lobby; (3) to (7) as this plan
  recommended. All seven are recorded in "Lead rulings" at the end.

**Estimate:** about 5 agent-days, 11 tasks in 4 waves. The spec says 4. The extra half day is `over{tick, result}`,
which the spec assumed matchmaking P0 would have built; the other half day is the declared bot model (ruling 2: the
parser, the column, the two displays and Task 3.11's bot clients).

## §0. The spec checked against the code (origin/main `e8da5117c`)

These facts come from reading the code. Where one disagrees with the spec, this plan follows the code and says so.
**Ruled** items are this plan's decisions. Items the lead decided are marked **Ruled (lead)** and listed in "Lead rulings" at the end (11 Nov).

**What A0 to A2 already built for A3**

1. **The schema is on main.** `match_record`, `match_seat` and the index `match_seat_member (member_id, started_at)` are
   in `0001_members.sql`, exactly as spec §2.2 has them. **No column is missing for A3**, so A3 adds no migration
   (ruling 3). Ruling 2's declared bot model goes in the existing `match_seat.bot_label TEXT` (§0.16). That column's SQL
   comment ("a bot preset's label (arena), never text a person typed") is stale after ruling 2; a comment binds nothing,
   and `0001_members.sql` is not edited (Global Constraints), so the as-built note in Task 3.10 records it instead.
2. **Delete and export already cover the match tables.** `tables.ts`'s `MEMBER_TABLES` row for `match_seat` sets
   `member_id = NULL, kind = 'deleted'`, and `MATCH_ORPHAN_SWEEP_SQL` drops a `match_record` left with no member seat, in
   the delete batch and so in the 36-month sweep too. The export already joins `match_seat` to `match_record`. A3 adds
   the tests that use real rows (A3-5) and does not change either path.
3. **`PATCH profile` already takes `showRecord`** (`profile.ts`), and `GET me` already answers it. The app's profile
   screen does not show it yet. A3 adds the toggle and nothing on the server for it.
4. **`ACCOUNTS` is still unbound on main.** `wrangler.jsonc` has no `ACCOUNTS` database and no `ACCOUNT_TOMBSTONES`
   namespace: A1's Task 1.11 (lead-gated) has not run. Every account route answers 503 until it does. **Ruled:** every
   A3 path treats an unbound `ACCOUNTS` as "no member": create and join seat guests, the room writes nothing, and nothing
   errors. So A3 can merge before 1.11. The lead's gate match (Lead steps) can only be played after 1.11 (ruling 6).

**The versus room as it is**

5. **`over` carries only a tick.** `ClientMsg` is `{ t: 'over'; tick: number }` (`packages/net/src/protocol.ts`), and
   `room-core.ts` keeps `st.over: [number, number]`, the first tick each seat reported, only to arm the room's own close
   (`armClose`). Matchmaking P0's `over{tick, result}` has not landed. **Ruled:** A3 builds it (Task 3.1), as spec §5.2
   says to when P0 is late.
6. **There is no `match_result` table in the telemetry database.** Spec §5.2's last line, "The telemetry database's
   `match_result` (for `/stats`) and this table are written by the same room code path", describes P0, which is not
   built. **Ruled:** A3 writes the accounts database only. P0's telemetry row, with its `pid` and its pepper secret, stays
   P0's. When P0 lands it must take its result from the same `recordOf` draft (Task 3.2), so the two cannot disagree.
7. **A room can end with `left` after the sims decided it.** Today a winner who closes the tab after the end panel sends
   `bye`, and the room ends `left` naming the WINNER (`seatMessage`, `case 'bye'`: `left` is not refused once the close
   is armed). The client ignores it, because `matchResult` prefers the sim's own result. A record that read
   `endedReason` would book that win as a loss. **Ruled:** a settled `over` result wins over any room ending that comes
   after it (Task 3.2, test `a_winner_who_leaves_after_the_result_still_wins`).
8. **The seat's side is not its seat.** In a KDF v Sarim room the KDF seat is side 0 whichever seat hosts
   (`sidesOfFactions`). `MatchResult.side` is a SIDE. **Ruled:** the wire result names a SEAT (`winner: Seat | null`).
   The client converts with `config.seats[s].side` before it sends (Task 3.1, test `the_result_names_a_seat`).
9. **A seat's `kind` is asserted by the client** (`seatKindField`; `routes.ts`'s header says so). So "Bot" in a record
   means "a seat that said it was a bot". **Ruled:** a seat with a valid session is a `member` seat whatever kind it
   claims (the room still paces on the claimed kind, as today). A seat with no session is `bot` when it claimed bot, else
   `guest`.
10. **The room's existing D1 writes go to `env.DB`** (`writeDesync`, `writeSnapMismatch`), awaited inside `apply` after
    the sends and wrapped so a failure never breaks the room. The record follows the same pattern against
    `env.ACCOUNTS` (Task 3.4).
11. **A room is purged 2 minutes after it ends** (`PURGE_AFTER_MS`), and a Durable Object can be evicted between any two
    events. **Ruled:** the record write is guarded by a flag persisted with the room state (`recorded`), and by
    `INSERT OR IGNORE` on the primary key `(code, started_at)`, so a re-run after an eviction writes nothing twice.
12. **There is no start time in the room state.** `RoomState.createdMs` is the create time. A code is minted fresh per
    room and wiped at purge, so `(code, createdMs)` is unique, but a lobby can wait. **Ruled:** `RoomState` gains
    `startedMs`, set when `start` is sent (status leaves `lobby`). A room persisted before A3 reads `createdMs` instead.

**Identity and privacy, checked against the spec**

13. **Spec §5.1 puts `member: <public_id>` in the seat ticket.** The ticket is a client-readable JSON payload
    (`b64url(json).hmac`), and the room never needs the member from it: the seat is fixed at `/create` and `/join`, and
    the room's meta can hold the member beside the callsign. **Ruled:** the ticket is unchanged. The Worker sends the
    member to the room in its own `https://room/create` and `https://room/join` request, which no client can reach, and
    the room keeps it in `RoomMeta.members`. That request is built field by field today, so a client field named `member`
    cannot pass through it (A3-2 sends one anyway).
14. **Member labels stay out of `MatchConfig`.** `config` is written whole to the telemetry database's desync log
    (`logDesync`), carried in replay files (`replay-file.ts`) and attached to feedback reports. A public id or display
    name there would link telemetry to a member (L10, A1-10). **Ruled:** the labels travel only in the `lobby` message
    (`SeatState.member`, added by the room's `lobbyFor`). The app keeps the last lobby's labels and passes them into the
    battlefield, whose HUD, chat and score names read `seatLabel(seat)` instead of `config.seats[seat].callsign` (Task
    3.7). A member's typed callsign stays in `config`, as today.
15. **A1-10 contradicts §5.3.** A1-10 says the opponent's lobby message is searched for the member's public id and
    display name, but §5.3 (and L11) show both to the opponent. **Ruled:** the lobby half of A1-10 searches for the
    session token, the SteamID and the internal member id, which must never appear. The public id and the display name
    must appear in the lobby and nowhere in telemetry, the desync log, a replay header or the feedback context (Task
    3.10).
16. **The bot label has no trustworthy source, so the operator declares it (ruling 2).** §5.3 stores `bot_label`, "a
    preset's text, never typed by a player". Arena presets are local operator files (`tools/src/net/arena-presets.ts`),
    and no wire field carries a preset id: a bot sends a `callsign`, which its operator types (`pnpm bot -- --callsign`).
    **Ruled (lead, 11 Nov):** a bot seat declares the model that drives it, a listed id from `BOT_MODELS` in `@lions/net`
    or `other` plus a typed name (self-trained models are expected). The declaration is a LABEL, never identity: it does
    not make a seat a bot, a member or a guest (§0.9 decides that), it moves no W-L, and a seat with a session (a member
    seat) or a human seat drops it. The design, end to end:
    - **Where it is declared.** The bot client, at join or create: `pnpm bot` (Task 3.11) derives it from `--model` (an
      alias or listed id is that id; any other value is `other` with the value as the name) or takes `--model-name
      <text>` for "Other"; the arena (`tools/src/net/arena.ts`, both seats) sends the preset's id when it is a listed id,
      else `other` with the preset's `label`; a scripted arena player sends `scripted`. `agent.ts`'s `joinRoom` gains an
      optional `botModel` argument. The browser never sends one.
    - **How it reaches the room.** A new body field `botModel` on `POST /api/match` and `POST /api/match/:code/join`,
      parsed by `botModelField` (Task 3.3) and put field by field into the Worker-to-room request, as the member is
      (§0.13). The room keeps it in `RoomMeta.botModels`, and only for a seat whose kind is `bot`.
    - **Never in `MatchConfig`** (§0.14's rule, for the same reason: typed text must not reach the desync log, a replay
      or a feedback report). It travels in the `lobby` message only (`SeatState.botModel`, Task 3.5).
    - **Storage.** `match_seat.bot_label` (already in `0001_members.sql`): **no migration.** The column holds an encoded
      form, `id:<listed id>` or `other:<cleaned name>` (`encodeBotModel` / `decodeBotModel`, Task 3.3), so a typed name
      that happens to equal a listed id can never pass as the listed label. Written only on a `bot` seat row with no
      member; a guest row and a member row keep `bot_label` NULL.
    - **The typed name's limits.** Cleaned by `cleanCallsign` itself (control and format characters, NFKC, whitespace,
      the `MAX_CALLSIGN_CHARS` = 24 code-point cap): the same cleaning as a callsign, on the client and again on the
      Worker. The Worker trims an over-long name to the cap (it trusts nothing and must not lose the seat); `pnpm bot`
      refuses one before it joins, as it refuses a long `--callsign`. `other` whose name is absent or cleans to `''` is
      refused with 400 `botModel`, and so is an id not in `BOT_MODELS`. An absent `botModel` is fine: the seat is an
      unlabelled bot, shown as "Bot" (an old bot client keeps working).
    - **The list.** `BOT_MODELS` in `packages/net/src/bot-model.ts`: `scripted`, `claude-opus-5-5`, `claude-sonnet-5-5`,
      `claude-haiku-5-5`, `claude-fable-5-2`. Append-only, because stored rows name ids (a test pins the literal list
      prefix). Each id's display label is the catalogue key `bot.model.<id>` in `en.json`.
    - **Display.** History (Task 3.8) and lobby (Task 3.7) show a listed id through `t('bot.model.<id>')` and a typed name
      as DATA (a text node, never through `t()`, never as HTML), beside the Bot tag. A stored value that does not decode
      (an unknown prefix) reads as an unlabelled bot.
    - **Moderation.** The typed name is user text stored beside a member's history, so the `/stats` blank action (Task
      3.9) also blanks it: `POST /stats/api/bots/blank { name }` sets every `bot_label = 'other:' || <cleaned name>` to
      NULL. A live lobby is not reached; it lasts minutes.
    - **Review.** The parser and the room request are in Task 3.3 and the write in Task 3.4, both Opus-reviewed (ruling
      5): it is user text crossing the Worker into the accounts database.
17. **The display name of a new Steam member is its public id** (A0/A1 §0.15). Blanking a name from `/stats` therefore
    resets it to the public id. **Ruled (lead, ruling 3):** no lock and no migration; the member may rename again.
18. **The public id is 8 characters.** §5.3's example, "Ilan · K7Q2", shows 4. Four Crockford characters are 20 bits and
    collide among about a thousand members, which defeats "the public id tells two people apart". **Ruled:** the label
    shows all 8 (`Ilan · K7Q2M4XA`).
19. **W-L counts every agreed result (ruling 1).** Guest, bot and member opponents alike, once the record is agreed
    (§0.23, §0.24, or a room decision with no settled report); a disagreed or voided room writes no record, and a lone
    report is `agreed = 0`, so neither ever counts. **Accepted risk (lead, 11 Nov):** a member can farm W-L by beating
    their own signed-out second tab or a client that claims to be a bot; versus pays 0 coins, so it moves only the number.
20. **Records and the accounts switch.** Sign-in works while the switch is closed (A1-13), so a member exists then.
    **Ruled:** recording does not read `flags.accounts`. It reads its own breaker, `flags.records` (below).
21. **A breaker for the records.** The room writes about 4 rows per recorded match into the shared D1 day budget.
    **Ruled:** a record reads `acct-all` first and skips the write (logged once) when the day is spent, as `opBudget`
    does. A record does not bump the member's `acct-ops`: the room is not a request, and two members share one record.
    The lead can stop every record write with `flags.records = 'closed'`, with no deploy. **Ruled (lead, ruling 4):** a
    missing row means records are written.

**What the spec does not say, ruled here**

22. **A sandbox room records nothing.** It is two humans on one side, with no winner (`forfeitApplies` already treats it
    so). Records are for `mode === 'versus'` only.
23. **Two `over` reports that disagree void the record for good**, whatever ending follows, even when the ticks match
    and only the results differ. `armClose` keeps comparing ticks only, so the room's close is unchanged.
24. **The hash rule.** P0 says "the last hash pair at or before that tick agreed". A room that desyncs ends `void`, so a
    room still alive has had every compared pair agree. **Ruled:** an agreed record also needs
    `st.lastHashTick >= overTick - config.hashEveryTicks`: the newest compared pair is at most one hash period before
    the result tick. Task 3.2's loop test measures that an honest pair meets it.
25. **A member deleted mid-match.** `match_seat.member_id` references `member`, so a plain insert of a deleted member's
    id fails the foreign key and loses the whole record. **Ruled:** a seat row's `member_id` is
    `(SELECT id FROM member WHERE id = ?)`, and its kind is `deleted` when that is NULL. The other member keeps the match.
26. **W-L in the lobby is read at create and join.** The Worker reads it with the member and the room holds it for the
    room's life. A record written during the lobby (impossible: one room per code) cannot make it stale.

## Global Constraints

- The sim is untouched. `pnpm test:determinism` passes before and after every task, and nothing under `packages/sim/`
  changes.
- **No migration and no binding.** `packages/worker/migrations-accounts/` keeps `0001_members.sql` alone (ruling 2's
  model label uses its existing `bot_label` column), and `wrangler.jsonc` is not edited. With `ACCOUNTS` unbound, every A3 path behaves as a guest-only room (§0.4).
- **Identity comes from the cookie, never the body.** Only `seatMemberOf` (Task 3.3) reads the session for a seat. No
  field of a create or join body becomes a member, a public id or a record.
- **Nothing identifies a guest.** No accounts row holds a guest's callsign, `lions.versus.player` id or seat token. A
  guest seat row is `{ seat, kind: 'guest', side }` and nothing else. A bot seat's declared model (§0.16) is a bot
  row's `bot_label` only, never a guest's.
- **Agreed results only.** A record is written only from `recordOf` (Task 3.2). Agreed means both seats reported the
  same result on the same tick and the hash rule (§0.24) holds, or the room decided it (`surrender`, `forfeit`, `left`)
  with no settled `over` before it. A lone report is written with `agreed = 0`, and no W-L ever counts it. Every
  agreed record counts in W-L, whoever the opponent was (ruling 1).
- **Versus pays 0.** No A3 file imports `@lions/economy`, writes `wallet` or writes `coin_journal`. `worker/src/match/**`
  never imports `@lions/economy` (G-V2, eslint).
- **Labels never in `MatchConfig`** (§0.14), the declared bot model included (§0.16). The internal member id never leaves the server: not in a ticket, a lobby
  message, an answer or a log line.
- **Dependency direction:** `worker/src/match/` may import from `worker/src/account/` the read helpers this plan names
  (`resolveSession`, `seatMemberOf`, `writeMatchRecord`). `account/` never imports from `match/`. `@lions/net` gains
  types and parsers only.
- No `any`, no non-null assertions. `pnpm typecheck` with lint.
- Every chrome string goes through `t()` and `en.json`; `pnpm validate:ui` passes. Issue refs are GH-NNN.
- **Constants (new):**
  - `packages/net/src/protocol.ts`: `RESULT_BYS = ['annihilation', 'objective', 'stalemate', 'time', 'mutual'] as const`
    (the sim's own endings), and `RECORD_REASONS = [...RESULT_BYS, 'surrender', 'forfeit', 'left'] as const`;
  - `packages/worker/src/account/config.ts`: `MATCHES_PAGE = 20`, `MATCHES_PAGE_MAX = 50`, `RECORD_ROWS = 4` (the rows a
    record writes, read against `acct-all`);

- House rules: no `git add -A` (use `git commit -- <paths>`), no `git checkout <file>`, no `git stash`. No local

## Review Focus

1. **A forged body.** A create or join that names another member's public id, internal id or `member` field, with no
   cookie, seats a guest; with a cookie, the cookie's member and nothing else. (Task 3.3, A3-2.)
2. **A liar.** One seat reports a win and the other a loss: no record, ever, even if the liar then surrenders or leaves.
   (Task 3.2, A3-1 and §0.23.)
3. **A winner who closes the tab.** The record still names them the winner. (Task 3.2, §0.7.)
4. **A guest in the opponent's history.** The accounts database holds no trace of their callsign or ids, and the
   history reads "Guest". (Tasks 3.4 and 3.8, A3-3 and A3-4.)
5. **A desync log, a replay and a feedback report from a member's match** hold no public id and no display name.
   (Task 3.10, §0.14.)
6. **A typed bot model name** (§0.16): cleaned by `cleanCallsign` on the Worker, capped, stored only on a bot row,
   shown as data and never as HTML or through `t()`, out of `MatchConfig`, and blankable from `/stats`. (Tasks 3.3, 3.4,
   3.7, 3.8, 3.9.)

## The wire contract

Types in `packages/net/src/protocol.ts` (the room messages) and `packages/economy/src/account-wire.ts` (the account
route), so client and server cannot drift.

```ts
// @lions/net
export type ResultBy = (typeof RESULT_BYS)[number];
export type RecordReason = (typeof RECORD_REASONS)[number];
/** What one seat's sim decided, by SEAT (§0.8). `winner: null` is a draw. */
export interface OverResult { winner: Seat | null; by: ResultBy }
// ClientMsg: { t: 'over'; tick: number; result?: OverResult }   result absent = a client from before A3: it never agrees
/** A member seat's label, in the lobby only (§0.14). `record` is present only when that member shows it. */
export interface SeatMember { name: string; publicId: string; record?: { won: number; lost: number; drawn: number } }
/** A bot's declared model (§0.16): a label, never identity. `name` is cleanCallsign'd, 1 to 24 code points. */
export type BotModelId = (typeof BOT_MODELS)[number];
export type BotModel = { id: BotModelId } | { id: 'other'; name: string };
// create and join bodies gain: botModel?: BotModel   (absent = an unlabelled bot; malformed = 400 'botModel')
// SeatState gains: member?: SeatMember; kind?: 'human' | 'bot'; botModel?: BotModel   (kind absent reads human)
```

```ts
// @lions/economy account-wire.ts
export type MatchOpponent =
  | { kind: 'member'; name: string; publicId: string }   // the name as it is NOW (§5.3)
  | { kind: 'guest' } | { kind: 'bot'; model: BotModel | null } | { kind: 'deleted' };   // model: §0.16, decoded from bot_label
export interface MatchView {
  code: string; startedAt: number; endedAt: number; map: string; matchup: string; winMode: string | null; kit: string;
  reason: RecordReason; ticks: number; agreed: boolean;
  you: { seat: Seat; side: string }; opponent: MatchOpponent;
  outcome: 'won' | 'lost' | 'drawn';                       // from winner_seat; agreed: false shows "unconfirmed"
}
export interface MatchesAnswer { matches: MatchView[]; next: number | null; record: { won: number; lost: number; drawn: number } }
```

| Route | Auth | Body or query | 200 answer | Other answers |
|---|---|---|---|---|
| `GET /api/account/matches` | session | `?before=<startedAt>&limit=<n>` (default 20, max 50) | `MatchesAnswer` | 401, 400 `query` |
| `POST /api/match`, `POST /api/match/:code/join` | the cookie, optional | unchanged | unchanged (no member field in the answer) | unchanged |
| `POST /api/match`, `POST /api/match/:code/join` (bot) | none (a bot has no session) | `botModel?: BotModel` added | unchanged | 400 `botModel` (unknown id; `other` with no usable name) |
| `POST /stats/api/members/blank` | the `/stats` session, same origin | `{ publicId }` | `{ ok: true }` | 403, 404, 400 |
| `POST /stats/api/bots/blank` | the `/stats` session, same origin | `{ name }` (a typed model name) | `{ ok: true, changed: n }` | 403, 404 (none matched), 400 |

`GET matches` is a read: no `op_id`, no budget, as `GET state`.

## Risks

1. **The hash rule could refuse honest matches** (§0.24). If clients stop sending hashes once their panel is up, the
   last compared pair could trail the result tick by more than one period. Task 3.2 Step 2 measures it on the real loop.
   If it fails, the fallback is to compare against the last hash tick when the FIRST `over` arrived; that is a change of
   rule, so it is reported, not made silently.
2. **One room, one write, on a Durable Object.** The write runs after the sends, as the desync log does. A D1 outage
   loses that match's record (logged), never the room. The private test will show whether that is ever seen.
3. **`kind: 'bot'` and its model are claims.** A human can claim to be a bot, declare any listed model or type a name,
   and appear as that in a member's history; and since every agreed result counts (ruling 1), a member can farm W-L
   against their own second tab or a self-declared bot. The lead accepted that risk on 11 Nov: versus pays 0, so it moves
   only the number. A rude typed model name is blanked from `/stats` (Task 3.9).
4. **Everything is behind the session.** CI's browser walks never sign in, so the unit tests and the lead's gate match
   are the only witnesses. At most one Metal browser check, on the implementer's own port with music off, after Task 3.7:
   a guest-only lobby, asserting the Guest tag and zero `/api/account` requests without `?accounts`.
