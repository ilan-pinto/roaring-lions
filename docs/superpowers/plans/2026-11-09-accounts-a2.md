# Accounts A2: claim and sync, server coins, the prompt (plan, GH-1075)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A signed-in player's campaign, brigade, save slots and Roar coins move to the server once (the claim) and then
sync through a server-backed `LedgerStore`. The server alone moves coins: it takes facts, never amounts.

**Architecture:** The Worker gains the A2 routes under `packages/worker/src/account/`. They write through one
compare-and-swap writer for the wallet and one for the campaign, so the coin journal always balances. The pure rules
both sides need (ledger and slot validation, the store input, canonical blobs, the claim's evidence) move into
`@lions/economy`. The app gains `accountLedgerStore`, which implements the existing synchronous `LedgerStore` over a local
cache and an outbox, plus a background sync loop, the claim, the Stores' pending Buy and the debrief prompt. Everything
stays behind `?accounts` and the closed switch. **No migration and no binding:** the routes answer 503 until Task 1.11
binds `ACCOUNTS`, as they do today.

**Tech Stack:** TypeScript strict, Cloudflare Workers, D1 (`node:sqlite` in tests through `test-d1.ts`), vitest, jsdom,
Web Crypto, Web Locks.

**Spec:** `docs/superpowers/specs/2026-11-07-accounts-profiles-design.md` §2.3 to §2.7, §3, §4, §7 (A2). Read it with the
A0/A1 plan, `docs/superpowers/plans/2026-11-08-accounts-a0-a1.md`, whose §0, its "Carried to A2" section and the lead's
8 Nov rulings bind this plan. Lead rulings on GH-1075 (7 and 8 Nov): L5 (coins server-strict; campaign, credits and slots
trusted), L6 (coins merge by difference; a second device's campaign arrives as a slot), coupon coins in a claim credited
and capped, the switch opens after A1.

**Estimate:** about 7.5 agent-days, 14 tasks. The spec says 7; the extra half day is the GH-1142 guard, the two-tab
lease and the privacy page amendment.

## §0. The spec checked against the code (origin/main `50e5eaa5b`)

These facts come from reading the code. Where one disagrees with the spec or the A0/A1 plan, this plan follows the fact
and says so. **Ruled** items are this plan's decisions under the no-questions rule. **Lead** items are batched in "Lead
decisions" at the end.

**What A0 and A1 left**

1. **`earnDifference` has no `raised`.** The A0/A1 plan (Task 0.5, review item 781) promised
   `{ coins, record, raised }`. `packages/economy/src/earn.ts` on main returns `{ coins, record }` only. **Ruled:** Task 2.1
   adds `raised` exactly as Task 0.5 specified, and the claim raises `wallet.earn` by `raised` alone.
2. **`ACCOUNT_BODY_MAX_BYTES` is 4096** (`config.ts`), and `readAccountBody` takes no cap. A campaign is up to 256 KiB.
   **Ruled:** `readAccountBody(req, max = ACCOUNT_BODY_MAX_BYTES)`, and three new caps (Global Constraints).
3. **The day budget is bumped before the op lookup.** `patchProfile` calls `opBudget` and then `withOp`, so a retry of an
   op already answered burns a write of the member's 400. An outbox retries by design. **Ruled:** A2 routes go through
   `budgetedOp` (Task 2.3): the stored answer first, then the budget, then `withOp`. `opBudget` also adopts M1's
   read-first order from `startBudget` (PR 1133): the overall count is read before the member's row is bumped, so a
   spent day writes nothing. A1's `patchProfile` moves to `budgetedOp` in the same task.
4. **The server wallet has no `receipts` column**, and the Stores' Receipts shelf reads `RoarWallet.receipts`. **Ruled:**
   every journal row's `detail` carries the receipt the economy function appended (`detail.receipt`), and the wallet the
   server answers is built with `receipts` = the member's last `RECEIPT_CAP` journal receipts, oldest first. One format,
   no migration.
5. **No table holds the mission start nonce.** **Ruled:** `POST mission/start` is a `withOp` write of kind
   `mission.start`, response `{ start, missionId, at }`. A victory that uses it rewrites that row's `kind` to
   `mission.start.used` in its own batch. A replay of the start's `op_id` still returns the stored answer, because the
   lookup ignores `kind`. `account_op` is swept after 30 days (A1), and a nonce older than `START_MAX_AGE_MS` (7 days)
   pays nothing.
6. **D1 has no row-level compare-and-swap, and a lost update breaks the journal.** Two spends that both read `free = 100`
   would both write 50, journal −50 twice, and leave `free` 50 with `SUM(free_delta)` 0: a double spend that also breaks
   the A2-8 invariant. **Ruled:** the wallet and campaign writers guard on the revision they read, through the schema's
   own CHECKs, so a stale write fails and D1 rolls the whole batch back:
   - `UPDATE wallet SET free = CASE WHEN revision = ?r THEN ?free ELSE -1 END, ..., revision = revision + 1 WHERE member_id = ?m`
     (`-1` fails `CHECK (free BETWEEN 0 AND 1000000)`);
   - `UPDATE campaign_state SET bytes = CASE WHEN revision = ?r THEN ?bytes ELSE 262145 END, ..., revision = revision + 1 WHERE member_id = ?m`
     (`262145` fails `CHECK (bytes <= 262144)`).

   A route whose batch fails `CHECK constraint failed` re-reads and re-prices, up to `CAS_TRIES` (3), then answers 409
   `busy` (the loop's place and its guard against a real bug are §0.32 and §0.35). Every journal row is built from the same read the guard checks (`free_delta = after - before`), so the
   journal balances by construction. Test A2-24 (plan) races two spends.
7. **Only `account/client.ts` may name `/api/account`** (`client.test.ts`, "only account/client.ts names /api/account").
   **Ruled:** every new request is a method on `AccountClient`. The sync loop and the claim call those methods.
8. **`LedgerStore` is synchronous, and a victory is three writes.** `writeVictory` calls `writeLedger`, `writeRoar` and
   `writeAccount` in turn, so a store behind the door cannot tell they are one victory. **Ruled:** `LedgerStore` gains
   `recordVictory(v: VictoryRecord): VictoryWrite`. The guest store's is today's `writeVictory`, byte for byte, and
   `settleVictory` calls it. `accountLedgerStore`'s queues one `victory` op. The module header's "eleven methods" count
   is updated.
9. **Coins are never written through the door while signed in.** Today `writeRoar` is called by the coin Buy (`main.ts`),
   `redeemOnStore`, `resetAccount` and `writeVictory`. **Ruled:** each of those becomes a server call when signed in
   (spend, coupon, reset-free, victory), and `accountLedgerStore.writeRoar` throws `ServerCoinsError`. Every coin path's
   test drives the account store, so a path left on `writeRoar` goes red on the throw.
10. **The Stores' and Garage's handlers are synchronous** (`stores.onBuy`, `onRedeem`, `onReset` return `GarageState`).
    The spec's "the button shows its pending state" needs an async answer. **Ruled:** each may return
    `Promise<GarageState>`. While it is pending the control is disabled and reads `stores.pending` (Task 2.12).
11. **`ledgerStore` is a module constant built at import** (`main.ts` line 434). **Ruled:** `selectLedgerStore(query,
    storage)` decides once, synchronously, from the binding and the cache: a claimed binding (`claimedAt`) with a cache
    and `accountsEnabled(query)` gives `accountLedgerStore`; anything else gives today's `browserLedgerStore`. With a
    claimed binding and no cache, boot awaits `GET state` (5 s) before the first screen mounts. On a timeout the menu
    says `account.unreachable` and the campaign entry is disabled; the guest keys are not read (they were removed by the
    claim).
12. **Server spend pricing needs code that lives in the app** (A0/A1 §0.7): `garageUnits` and `coinHalf` inside
    `main.ts`, `kdfUnlockGate` (`kdf-gate.ts`), `buildCoinHalf` (`credit-buy.ts`), `sanitiseLedger` (`ledger-shape.ts`)
    and `importSlot`'s validation (`profile.ts`). All are pure. **Ruled:** Task 2.1 moves them, and adds
    `storeInputFor`, which `main.ts` then calls, so the Stores and the server build a `StoreInput` one way. The
    `kdfBrigadeTraits` stay in `main.ts`: `storeItems` never reads them.
13. **`sanitiseLedger` and `migrateAccount` rewrite what they clean**, so a digest of the bytes the server stored can
    differ from a digest of the bytes the device sent, and a claim of a cleaned ledger would never complete. **Ruled:**
    both sides digest one canonical form, `canonicalCampaign` and `canonicalSlot` (Task 2.1), through Web Crypto
    SHA-256 over UTF-8. Never the economy's pure-JS `sha256Hex`, which is for coupon codes: on a 256 KiB blob it would
    spend Workers Free's 10 ms of CPU.
14. **The coupon table is one code with two grants** (`data/coupons.json`: `lead_special_units_10k` gives credits,
    `lead_roar_coins_100k` gives coins, under one hash). Credits are a brigade field. **Ruled:** `POST coupon` applies
    both halves server-side in one batch: coins to the wallet, and credits to `campaign_state.brigade` through
    `redeemCoupon` run on a brigade whose `coupons` list is the member's `coupon_use` ids. So a reset that empties the
    brigade cannot reopen a coupon (A2-11), and the grant and its use land together.
15. **`lions.saves` keeps damaged entries verbatim** (`profile.ts`, `DAMAGED_BLOB_ID` and per-id damage). **Ruled:** a
    claim never sends a damaged entry. The client files each one in `lions.account.local` with reason `invalid` before
    `lions.saves` is removed.
16. **A sign-out followed by new guest play would be swallowed by the claim's idempotency.** The binding keeps
    `deviceId`, `device_claim(member, device_id)` returns the stored result, the digests do not match the new
    progress, and the claim retries forever. **Ruled:** sign-out and account deletion clear the binding's `deviceId`,
    and the next claim mints a new one. `earn_lifetime` is what stops a double pay, never the device id (spec §3.5).
    Test A2-30 (plan).
17. **Two tabs share `lions.account.cache` and the outbox.** Each tab's view lives in memory, so a second
    tab's write could overwrite the first tab's outbox. **Ruled (amended by §0.38: one outbox key per tab):** the
    flusher runs under `navigator.locks.request('lions.account.flush')`, so one tab sends at a time and re-reads
    the outbox before each send. A tab re-reads the cache on the `storage` event. With no Web Locks the tab flushes
    alone; a 409 then keeps the other tab's campaign as a conflict slot, which loses nothing. Test A2-31 (plan).
18. **A queued campaign op is a whole snapshot**, so replaying it over a server answer that already holds a coupon's
    credits or a reset would put the old brigade back. **Ruled:** spend, coupon and reset-free are **barrier ops**. They
    are never queued, they are sent only when the outbox is empty, and they are disabled offline or while it drains
    (reason line `stores.syncing` or `stores.offline`). This is also GH-1142's mirror: a coin Buy priced against a
    server brigade that lacks a queued credit tier.
19. **The spec has no route to fetch one slot's body.** `GET state` carrying 16 slots of 256 KiB each would cost the
    Worker's CPU. **Ruled:** `GET state` answers slot metadata with a change token (`savedAt` and `bytes`, §0.44), and
    `GET slots/:id` answers one body. The client fetches a body whose token differs from its cache. The Saves screen shows `saves.downloading` on a slot
    without one, with Load disabled.
20. **A victory whose campaign is stale still won coins.** **Ruled:** a victory carries `base` like `PUT campaign`. Its
    coin half is a fact and is paid. Its campaign half follows the conflict rule (a `conflict` slot or `held`), and the
    answer is 200 with `conflict` set, never a 409.
21. **The welcome is paid by the claim's first win.** `earnDifference` pays the welcome when any evidence win exists
    and the record has none. A member who won online first has `earn_lifetime.welcomed`, so a later claim pays it
    again only if `welcomed` is false. Nothing to change. This is noted because A2-3's literal 135 depends on it.

**Security, checked against the spec**

26. **Claim forgery** is bounded by four things, each tested: the earn table with the 0 to 3 clamp and world missions
    only (A2-3, A2-4); the device balance read as a ceiling only (A2-3); `paid` ignored and fenced (A2-5); coupon coins
    capped per member (A2-22). A claim charges its carried entitlements against the coins **that claim** credited, never
    the member's balance, so device B cannot spend device A's coins (`claim_spends_only_its_own_coins`).
27. **Device ids are client-minted**, so a forger can claim from any number of them. Each pays 0 after the first
    (`earn_lifetime`), but each writes about 15 rows plus slots. **Ruled:** a per-member day budget of 5 claims
    (`acct-claim`), and at most 20 `device_claim` rows per member ever (`claim_cap`). Lead decision 6.
28. **Replay** is stopped three ways: `op_id` (`account_op`), `device_id` (`device_claim`), and the single-use start
    nonce (§0.5). None of them stops a double pay. `earn_lifetime` does (spec §3.5, A2-2, A2-20).
29. **Credits, the campaign and slots are trusted** (L5). The server builds the spend's `StoreInput` from the member's
    trusted campaign, so a forged ledger can open a unit to a coin Buy that it could also open to a credit Buy. That is
    the L5 line, not a new hole: free coins open only what single player opens (guard G3), and `networkView` never
    counts them.
30. **The CPU of a claim on Workers Free (10 ms).** A 1 MiB JSON parse plus canonicalisation is a few milliseconds,
    and the digests run in Web Crypto. That is close enough to the limit to be a risk, not a fact. Lead decision 5.

**The Opus review of PR 1160 (9 Nov), each finding ruled**

31. **The binding loses `deviceId` and `claimedAt` (BLOCKER).** `account/signed-in.ts` writes `{version: 1, publicId}`
    on every signed-in `me`, and `readBinding` rebuilds only those two fields. One boot after a claim, `claimedAt` is
    gone and the device would pick the guest store. **Ruled:** `readBinding` and `writeBinding` carry the optional
    fields. `resolveSignedIn` keeps them when the `publicId` matches and clears them for a different member. Task 2.9,
    test `binding_survives_me`.
32. **The order of the budget, the op log and the CAS retry.** `withOp` runs the batch itself, outside `build`, so a
    retry loop inside `build` never sees a CAS failure. **Ruled:** `budgetedOp` charges the budget ONCE, then calls
    `withOp` up to `CAS_TRIES` times while the batch throws a CAS failure. Each attempt re-runs `build`, which re-reads.
    There is no separate `withCas`.
33. **A 409 that writes rows, and its replay.** `build` returns no status, and `account_op` stores only the body, so a
    retried stale `PUT campaign` would read as a 200. **Ruled:** `build` returns `{ statements, status, response }`, and
    `withOp` stores `{"s": status, "b": body}`. A stored row without `s` (an A1 row) reads as 200. A stored body never
    holds a whole campaign: a `CampaignView` in it is reduced to `{ revision, digest }`. A client given a reduced or
    older campaign keeps `confirmed` and refreshes with `GET state`. It never moves `confirmed` backwards.
34. **The first campaign write.** A racing plain `INSERT` fails on `UNIQUE`, not on a CHECK. **Ruled:**
    `INSERT ... ON CONFLICT (member_id) DO UPDATE SET bytes = 262145`, so a lost race fails the CHECK like any stale
    write. The insert writes `revision = 1`. `base: 0` means "no campaign row yet", so a second device's base-0 write is
    stale. In every batch, the wallet statement comes first, then the campaign, then slots, then the op.
35. **A CHECK failure is not always a lost race.** **Ruled:** after a CHECK failure, `budgetedOp` re-reads the wallet
    and campaign revisions. It retries only if one moved; otherwise it answers 500, so a real bug does not wear the
    lost-race answer. On the client, an op that fails 5 times in a row with a non-network answer (5xx or `busy`) is
    filed in `lions.account.local` with reason `refused` and dropped, so one bad op cannot wedge the outbox.
36. **The slot caps and the device cap race.** They are read and then inserted, so parallel requests can each see 11.
    **Ruled:** every batch that adds a slot or a `device_claim` row ends with a count guard,
    `UPDATE member SET last_seen_day = CASE WHEN (<count>) <= <cap> THEN last_seen_day ELSE NULL END WHERE id = ?1`, which
    trips `member.last_seen_day`'s NOT NULL and rolls the batch back. `isCapFailure` (`/NOT NULL constraint failed: member.last_seen_day/`)
    maps it to 409 `cap` or `claim_cap`. There are three caps: 12 player slots, 4 system slots, and 20 devices.
37. **`test-d1.ts` is not safe under concurrency.** Its `batch` awaits between `BEGIN` and `COMMIT`, so a second
    concurrent batch's `BEGIN` throws and its `ROLLBACK` aborts the first. **Ruled:** Task 2.3 serialises batches in
    `openTestD1` through a promise queue. Moving `patchProfile` onto `budgetedOp` adds an `account_op` lookup, so
    `profile.test.ts`'s `racingD1(h.db, 2)` would stop racing and pass vacuously. It becomes `racingD1(h.db, 4)`, and the
    test asserts that the gate opened.
38. **Two tabs and one outbox key.** localStorage is not atomic across processes. **Ruled:** one outbox key per tab,
    `lions.account.outbox.<tabId>`, where the `tabId` is kept in `sessionStorage`, with a heartbeat
    `lions.account.tab.<tabId>` every 10 s. A tab appends to and removes from its own key only. Flushing is one tab at a
    time under the lock. A tab that holds the lock adopts an orphaned outbox (heartbeat older than 60 s) by appending its
    ops to its own key, then removing the orphan's. §0.17 is amended to this.
39. **A credit Buy during a coupon or a reset could undo it.** **Ruled:** while a campaign-writing barrier (coupon,
    reset-free) is pending, every control that writes the campaign is disabled with `stores.pending`: credit Buys, slot
    load and save, and New campaign. GH-1142's guard also covers a unit: a credit unlock of unit U is disabled while a
    coin Buy of U is pending (`pendingSpends` key `unit:<id>`, beside `<unitId>.<track>`).
40. **A claim could retry forever.** **Ruled:**
    - Before the send, `lions.account.claiming` (`{deviceId, digests, at}`) is written, and the guest store refuses
      writes until the claim resolves. The screens show the existing "not saved" path and `account.claim.moving`.
    - A stored result whose digests do not match what the device now holds means the device id is minted again and the
      claim re-sent (`earn_lifetime` prevents a double pay).
    - `finishClaim` writes in this order: the held items, the cache, the binding's `claimedAt`, then
      `removeGuestProgress`. A boot that finds a claimed binding and a cache removes any guest keys left over.
    - A refused binding write aborts before any key is removed.
41. **Empty claims would spend the device cap.** **Ruled:** a device with no guest progress sets `claimedAt` locally and
    makes no claim request. It then loads `GET state`.
42. **The claim's input is bounded.** **Ruled:** `device_id` must pass `validOpId`. A claim carries at most 32 slots
    and 16 coupon ids, and answers 400 `body` beyond that. Unknown coupon ids are not echoed in the result. The client
    builds the body under `CLAIM_BODY_MAX` by moving the oldest slots into `lions.account.local` with reason `size`
    before sending. A 413 is therefore not expected, and it is handled as `kept`.
43. **What a slot digest covers.** The server stores claimed slots under new ids, and `PUT slots` carries `name`
    separately. **Ruled:** `canonicalSlot` covers `{ savedAt, build, ledger, account, tutorialDone }`, never `id` or
    `name`. A test pins idempotence: `canonical(parse(canonical(x))) === canonical(x)`. The server digests exactly the
    canonical string it stores.
44. **`GET state` has no digest column to read.** Hashing up to 16 × 256 KiB on every `GET state` is the cost §0.19
    avoids. **Ruled (Lead decision 8):** no migration. `GET state` answers each slot's `savedAt` and `bytes` as its
    change token, and the client fetches a body whose token differs. Every server write of a slot sets `saved_at` to
    the write's time. Digests appear only in the answers to `PUT slots/:id` and `claim`.
45. **`CoinAsk` already exists** (`stores.ts`: `{ kind: 'unit' | 'tier', ... }`), and `index.ts` exports both with
    `export *`. **Ruled:** the wire type is `CoinAskWire` (`{ item: ... }`, the spec's wording), with
    `toCoinAsk(w: CoinAskWire): CoinAsk`.
46. **Explicit sign-out.** **Ruled:** sign-out first tries to flush the outbox (5 s). Ops still queued are filed in
    `lions.account.local` (reason `refused`). Then the cache, the outbox, `claimedAt` and `deviceId` are cleared, and the
    device is a guest with no campaign (spec §3.3). A boot that gets 401 with a claimed binding and no cache falls back
    to the guest store. A 401 with a cache is A1-21's read-only signed-out state.
47. **The win floor and the 2× speed** (`ui/hud.ts`). 2× uses up all of the "halved" margin. **Ruled (Lead decision
    9):** the floor is `floor(fastest / 4)`, a departure from the spec's "halved", so an honest player at 2× still
    clears it with a factor of 2 to spare.
48. **The review's minor findings, ruled:**
    - `walletWrite` throws when the entries' deltas do not sum to the wallet's change. It takes each entry's receipt
      explicitly, and an empty entry list with a moved wallet throws.
    - A2-21 gets a mutation aimed at the 925 assertion alone (pay the campaign bonus twice).
    - A2-8 asserts at least one op of every kind, and advances `now` a day at a time so the budgets do not end the run

    - The A1-2 CSRF test becomes table-driven over every non-GET route, and the A1-3 loop substitutes sample `:id`

    - The A2-27 scan excludes `test-kit.ts`.
    - The privacy page names the 30-day op log (mission start times). The unlinked test also searches for a device-id

    - `VictoryRecord` is defined in Task 2.9. `completedOf` is `profile.ts`'s private `slotCompleted`, exported from

    - `viewOf` applies the whole `roarEarn` wallet, earn record included, so two queued wins of one mission do not both

## Global Constraints

- The sim is untouched. `pnpm test:determinism` passes before and after every task, and nothing under `packages/sim/`
  changes.
- **No migration and no binding.** `packages/worker/migrations-accounts/` keeps `0001_members.sql` alone, and
  `wrangler.jsonc` is not edited. A2's routes answer 503 until Task 1.11 binds `ACCOUNTS`.
- **Dependency direction** as A0 ruled: `@lions/economy` imports `@lions/sim` and `@lions/data` only. `sim`, `net`,
  `render`, `app/src/net/**` and `worker/src/match/**` never import it (G-V2).
- No `any`, no non-null assertions. Run `pnpm typecheck` with lint.
- **Coins are the server's.** No request field is an amount or a price. `paid` stays 0 (`CHECK (paid = 0)`),
  `PURCHASES_OPEN` stays false, versus pays 0, and coins never move between members.
- **The journal balances:** `wallet.free = SUM(coin_journal.free_delta)` per member, after every route. Only
  `account/coin.ts` contains `UPDATE wallet` or `INSERT INTO coin_journal` among the non-test files under
  `packages/worker/src/account/` (test A2-27). `member.ts`'s A1 `INSERT INTO wallet` of an empty wallet and the delete
  path's `DELETE` statements are the only other statements that touch either table.
- **Ceilings, verbatim from the spec:** the lifetime earn ceiling is **925** (100 + 290 + 435 + 100); `MAX_COINS`
  1,000,000; a campaign or a slot is at most **262,144** bytes (canonical UTF-8); at most **12** `player` slots and,
  apart from them, **4** system slots (`claim` or `conflict`) per member.
- **Constants (new), in `packages/worker/src/account/config.ts`:**
  - `CAMPAIGN_BODY_MAX = 270_336` (256 KiB plus 8 KiB of envelope), for `PUT campaign`, `POST victory` and `PUT slots/:id`;

## The wire contract

Types only, in `packages/economy/src/account-wire.ts`, imported by `packages/app/src/account/client.ts` and by the Worker's
routes, so the two cannot drift. Every write body carries `op_id` (a UUID, `validOpId`). Every answer below may carry the
slide's `Set-Cookie` (A1).

```ts
export interface WalletView { free: number; paid: 0; entitlements: RoarWallet['entitlements']; earn: EarnRecord; receipts: RoarReceipt[]; revision: number }
export interface CampaignBody { ledger: LedgerData; brigade: BrigadeAccount; tutorialDone: boolean }
export interface CampaignView extends CampaignBody { revision: number; digest: string }
// `savedAt` + `bytes` is the change token (§0.44); `digest` is present only in PUT slots/:id and claim answers.
export interface SlotMetaView { id: string; name: string; savedAt: number; build: string; origin: 'player' | 'claim' | 'conflict'; bytes: number; digest?: string }
export interface ServerState { campaign: CampaignView | null; wallet: WalletView; slots: SlotMetaView[] }
export type ConflictAnswer = { slot: SlotMetaView } | { held: true };
export type InventoryItem =
  | { deviceId: string; status: 'stored'; serverId: string; digest: string }
  | { deviceId: string; status: 'rejected'; reason: 'cap' | 'size' | 'invalid' };
// Not `CoinAsk`: that name is stores.ts's `{ kind }` type (§0.45). `toCoinAsk` converts.
export type CoinAskWire = { item: 'unit'; unitId: string } | { item: 'tier'; unitId: string; track: string; tier: number };
```

| Route | Body | 200 answer | Other answers |
|---|---|---|---|
| `GET state` | none | `ServerState` | 401 |
| `GET slots/:id` | none | `{ slot: SlotMetaView; body: SaveSlot }` | 404 |
| `POST mission/start` | `{ op_id, missionId }` | `{ start: string; missionId; at: number }` | 400 `mission` (not a world mission) |
| `POST victory` | `{ op_id, missionId, stars, start: string \| null, base: number, campaign: CampaignBody \| null }` | `{ coins: number; awards: EarnAward[]; wallet; campaign: CampaignView \| null; conflict?: ConflictAnswer }` | 409 `busy`, 413 |
| `PUT campaign` | `{ op_id, base, ...CampaignBody }` | `{ campaign: CampaignView }` | 409 `{ error: 'stale'; campaign: CampaignView; conflict: ConflictAnswer }`, 409 `busy`, 413 |
| `POST spend` | `{ op_id } & CoinAskWire` | `{ wallet }` | 409 `{ error: 'refused'; reason: 'coins' \| 'closed'; wallet }`, 409 `busy` |
| `POST coupon` | `{ op_id, code }` | `{ result: 'ok' \| 'unknown' \| 'used'; ids: string[]; coins: number; credits: number; wallet; campaign: CampaignView \| null }` | 409 `busy` |
| `POST reset-free` | `{ op_id }` | `{ wallet; campaign: CampaignView \| null }` | 409 `busy` |
| `PUT slots/:id` | `{ op_id, name, savedAt, build, body: SaveSlot, origin?: 'player' \| 'conflict' }` | `{ slot: SlotMetaView }` | 409 `{ error: 'cap' }`, 400 `invalid` / `name`, 413 |
| `DELETE slots/:id` | `{ op_id }` | `{ ok: true }` | 404 |
| `POST claim` | `ClaimBody` | `ClaimResult` | 400 `body` (over 32 slots or 16 coupons, a bad `device_id`), 409 `{ error: 'claim_cap' }`, 413, 429 |

Every stored answer in `account_op` is `{"s": status, "b": body}`, with any `CampaignView` reduced to
`{ revision, digest }` (§0.33).

```ts
export interface ClaimBody {
  op_id: string;
  device_id: string;                 // a UUID (validOpId), minted by ensureDeviceId
  campaign: CampaignBody | null;     // null: the device has no campaign
  slots: { id: string; slot: SaveSlot }[];   // at most 32; valid slots only; damaged ones are never sent (§0.15)
  wallet: unknown;                   // the device's RoarWallet as stored; the server runs migrateRoar on it
  coupons: string[];                 // at most 16: brigade.coupons plus every coupon receipt's couponIds
}
export interface ClaimResult {
  coins: number;                     // net free coins credited by this claim
  earned: number;                    // the earn difference against earn_lifetime
  coupons: { id: string; credited: number; capped: boolean }[];
  carried: CoinAskWire[];
  notCarried: { ask: CoinAskWire; reason: 'coins' | 'closed' | 'owned' }[];
  campaign: InventoryItem | null;    // deviceId 'campaign'
  slots: InventoryItem[];            // one per sent slot, by the device's own id
  state: ServerState;                // read fresh, also on a repeated device_id
}
```

`reset-free` resets the wallet's free half (`resetFree`) and the brigade (`emptyAccount()`) in one batch: the server
form of the local reset's both-or-neither. `coupon_use` is untouched.

## Risks

1. **Workers Free's 10 ms of CPU on a large claim** (§0.30). A 1 MiB body is near the limit. If the private test logs
   error 1102 on `claim`, the fallback is a split claim: the claim carries the campaign and the wallet, and each slot
   follows as `PUT slots/:id` with `origin: 'claim'`, accounted in the same inventory by `device_id`. Lead decision 5.
2. **localStorage quota.** The cache holds slot bodies, the outbox holds whole campaigns, and the held list holds
   verbatim copies. A refused cache write leaves the page playing from memory (the spec's rule), and a refused held
   write keeps every guest key (A2-19). A device near the 5 MB quota may see "Not saved on this device" sooner than
   today.
3. **The CAS through a CHECK** (§0.6) depends on D1 reporting a constraint failure as an error and rolling the batch
   back, which D1 documents for `batch()`. `test-d1.ts` behaves the same. A2-24 is the witness; the risk is a production
   message text that `isCasFailure` does not match, which would answer 500 instead of retrying. `isCasFailure` matches
   `/CHECK constraint failed/i` and is logged once per failure, so the first production case is visible.
4. **The floor is a scripted plan's fastest win, halved.** A scripted plan has perfect information, so a human is
   slower, and halving leaves more room. A new mission without a playtest plan has floor 0, which pays as today.
5. **`?accounts` hides all of this from CI's browser walks.** `pnpm ui:routes` and the golden gate never reach the
   account store. The unit tests above are the only witness until the lead's private test. The agent runs at most one
   Metal browser check on its own port with music off, after Task 2.12: sign in is impossible without a binding, so the
   check drives the guest paths and asserts zero `/api/account` requests.

## Lead decisions (recommendation first)

1. **An offline-started mission's coins (CodeRabbit 709).** *Recommended:* the run records the win and pays no coins on
   the server, and the next online win of that mission pays its coins in full. The briefing says so before the mission
   starts. *Alternatives:* queue the start and judge the floor by when it reaches the server, which withholds coins
   silently; or skip both checks for an offline start, which makes the nonce worthless, because a forger would always
   claim to be offline.
2. **Signed-in coin Buys, coupons and the brigade reset need a connection and a synced outbox** (§0.18). *Recommended:*
   yes, with a reason line. Spending is already server-only in the spec, and the reset and coupons write the same
   brigade a queued campaign op would overwrite. *Alternative:* queue them, which re-opens the GH-1142 class of bug in
   both directions.
3. **The privacy page amendment ships in the A2 PR** (Task 2.14). The switch is open after A1 (ruling 2), so what A2
   stores must be on the page before A2 is live. *Recommended:* the lead merges the text with the PR. *Alternative:* hold
   A2's merge until the lead rewrites the page.
4. **Opus reviews Tasks 2.3, 2.5, 2.7 and 2.10** (the CAS writers and the journal, spending and coupons, the claim, the
   sync loop): the four where a mistake moves coins or loses a campaign. Sonnet implements every task and reviews the
   rest. *Alternative:* Sonnet everywhere, as the hard rules' default.
5. **The claim on Workers Free.** *Recommended:* stay on Free for the private test (L7), cap the claim body at 1 MiB, and
   split slots out of the claim only if error 1102 shows (Risk 1). *Alternative:* take Workers Paid (5 USD a month, 30 s
   of CPU) at A2 instead of A4.
6. **Claim limits.** *Recommended:* 5 claims a member a day, and 20 devices a member ever. A player past 20 is told to
   use Export and Import. *Alternative:* no lifetime cap, at the cost of unbounded `device_claim` rows from a script.
7. **No lead step before merge.** A2 adds no migration and no binding, so the spec's "apply any A2 migration" is empty.
   The lead's only A2 action is the merge. Task 1.11's bindings still gate everything going live. (This depends on
   decision 8.)
8. **How a device knows a slot changed** (§0.44). *Recommended:* no migration. `GET state` answers each slot's
   server-set `savedAt` and `bytes` as a change token, and digests appear only in write answers. *Alternative:* a
   `digest` column on `save_slot` (migration `0002`, which the lead applies before merge). That is exact, but it adds a
   lead step to A2.
9. **The win floor is a quarter of the fastest scripted win, not the spec's half** (§0.47). The HUD's 2× speed uses up
   the whole halved margin, and the withholding is silent. *Recommended:* a quarter. *Alternative:* the spec's half,
   with 2× wins sometimes paying no coins until the next online win.
