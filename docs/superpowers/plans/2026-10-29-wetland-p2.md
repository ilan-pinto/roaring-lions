# Wetland P2, wiring with stand-ins: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A fourth terrain theme, `wetland`, exists end to end, drawn with the art the game already ships. A
map can declare `"terrain": "wetland"` and use the marsh symbol `~`. The theme has its own tone bundle, its four
`theme_only` ramps, a per-theme ground-slot table, a family remap, the reed mat and the waterside willow pass. An
Ein Qasab greybox boots in Free Play. The shipped GLBs and ground images stand in, retinted through the bundle.
The phase ends on one capture run (own port, one Metal browser, music off, zoom 1 and 2.5) for **the lead's look at
the tones and the palette**. P3 (art) waits on that look.

**Nothing shipped moves.** No shipped map changes theme. Arid, green and highland compose the same terrain, compile
the same ground program and boot the same light, byte for byte. Task 1 pins all of that on all 35 shipped maps
**before** any wiring lands.

**Architecture:**

## What the code says, and what it changes about the spec's picture

Each point was read at `93eb0d09`. Read them before any task.

1. **Three themes, chosen per map.** A map's `terrain` (default `arid`) is parsed into `ParsedMap.terrain`
   (`map.ts` `TERRAIN_THEMES` set). `terrainTonesFor(map)` (`terrain-themes.ts`) returns the theme's bundle BY
   IDENTITY unless the map overrides its grove. `rendererOptionsFor` (`renderer-options.ts`) is the one route from
   a map to `RendererOptions`. Three `Record<TerrainTheme, ...>` tables exist: `TERRAIN_THEMES` and
   `TERRAIN_GROUND_TEXTURE` in `terrain-themes.ts`, and `GROVE_SPECIES_FAMILY` keyed by species. So adding
   `wetland` to `TerrainTheme` is a compile error in exactly the tables that need a row. The theme id and the
   bundle land in one task (Task 4).
2. **The four slot URLs are literals.** `renderer-options.ts` names `rock_ground_tile`, `rough_scrub_tile`,
   `orchard_floor_tile` and `knoll_scree_tile` for every theme. `ThreeRenderer.loadGroundTexture` looks the mean
   and repeat up in `GROUND_ALBEDOS` **by the URL's basename**. So a stand-in that names a shipped file needs no
   `mesh.ts` change, and P3 adds five `GROUND_ALBEDOS` entries when its images land.
3. **The terrain pin skips highland.** `terrain-defaults.test.ts` pins 24 maps, the non-highland ones (11 highland
   maps of 35 are unpinned). The digest is the full `composeTerrain` output (ground, scatter, residual and
   buildings meshes, decor and prop placements) through `rendererOptionsFor`. The golden scenarios `relief`
   (`tel_marum`) and `aftermath` (`qarn_hadid`) are highland, so the extension guards two gated baselines.
4. **No ground-program or light pin exists.** `GroundMaterial` is constructed with no arguments
   (`ThreeRenderer.groundMat`). `mesh.test.ts` reads its source through `onBeforeCompile` on the
   `meshphysical` chunks, and asserts contents, not identity. P2 adds no shader term, but P4's `THEME_WET` will.
   So the pin lands now, while it is trivially green.
5. **`familyFor` (`decor-place.ts`) tests `boulder` before everything but the ditch.** A `~` tile sets the
   boulder mask, so without a marsh branch BEFORE it, the marsh draws a boulder field: the ditch's lesson, again.
   `decorFamiliesFor` (`mesh-catalogue.ts`) mirrors that order and needs the same branch.
6. **`tileSurface` (`control-map.ts`) reads cover only on DECOR 0.** A `~` tile (decor 6, cover 1) falls through
   to `open`. The spec wants the scrub image under the marsh, so it needs its own branch. `groundTone`
   (`tones.ts`) gives a `~` tile the open wash, so the marsh floor (`tones.marsh`, `mud.3`) needs a branch there
   too. Both branches fire only on decor 6, which no shipped map carries.
7. **`paintMapTerrain` (`ui/map-preview.ts`) reads `blocked`, `boulder` and `cover` only.** A marsh paints as the
   rock tone. It needs optional `decor` and `marsh` inputs, which every shipped caller leaves out.
8. **Decor runs three passes** (`DECOR_PASSES = 3`, terrain / open ground / open scatter), and splices per tile.
   `changedDecorTiles` refuses a splice when `groveFamily` or `openScatter` differs BY REFERENCE. A fourth pass
   emits nothing on a theme without `waterside`. The terrain digest hashes `JSON.stringify(placements)`, not the
   `starts` array, so a shipped map's digest cannot move.
9. **The family list is closed in four places:**
   - `DecorFamily` (`decor-place.ts`);
   - `DecorFamilyName` (`mesh-catalogue.ts`, pinned against it by `mesh-catalogue.test.ts`);
   - `DENSITY` (a total `Record` over the non-clustered families);
   - `foliage-figure-ground.test.ts`'s `FOLIAGE_FAMILIES`.

   The tint key is `<family>:<role>`, read per placement (`decor-mesh.ts`). So a stand-in family that borrows
   another family's GLB still takes its OWN tint.
10. **The symbol census is pinned three ways:**
    - `map.test.ts` "exactly ten terrain symbols";
    - `terrain_symbols.test.ts`, which holds the validator's `TERRAIN_SYMBOLS` literal equal to `TERRAIN_LEGEND`;
    - `qarn_hadid_relief.test.ts` "authors every terrain symbol the legend declares", plus `toHaveLength(10)`.

    `~` is wetland-only, and `qarn_hadid` is highland, so the third CANNOT simply gain it. It is re-scoped to
    "every symbol legal on its theme".
11. **The art gate's quantiser targets every ramp, `theme_only` included** (`quantize_sprites.load_targets` has
    no theme filter; `karst` is in it today). The four new ramps join it. That can only change which on-palette
    entry a render pixel snaps to. Every mesh-gate check is alpha-based (IoU, framing) or on-palette by
    construction, so it cannot go red. `validate_assets.load_palette`'s allowed set widens by 13 colours. **CI's
    `validate:meshes` is the witness.** P2 runs no Blender.
12. **Adding a map moves these:**
    - `high_ground_maps.test.ts`: relief maps 24 -> 25, and `RISES` + `ein_qasab`;
    - `map-ids.test.ts`: `SHIPPED_MAP_IDS`;
    - `sandbox-menu.test.ts`: it requires `freePlay.map.<id>`;
    - `data/src/index.test.ts`: `maps` pinned to the directory;
    - `crown-summit.test.ts`: `SUMMITS[id] ?? 0`;
    - `shippedContentDigest()`'s VALUE. No test pins it to a literal, and any content change moves it.

    `scatter-density.test.ts` filters `family === 'grass' || 'sand'`, so on a wetland map the remapped
    `wet_grass` would leave its "0.65-1.0 a tile" check empty. That filter must learn the remap (Task 7).
13. **Props stay off the marsh by an existing rule.** `isForbiddenPropTile` refuses any `cover !== 0` tile, and
    `~` is cover 1. `scatter-density.test.ts` already asserts "never on a cover tile" for every map.
14. **`ground:capture` is the P2 camera.** It runs Metal (`gpuLaunchArgs('metal')`), music off, on ports 5193-5199,
    and refuses a held port. It takes per-map centre views at 0.35, 0.5, 1 and 2.5, a fogged view at 1 and a road
    close-up at 2.5. It has no marker views, so Task 8 adds `--markers=`.
15. **The spec puts the puddle-reflectance A/B in P2 (rev. 3, item 3). Puddles do not exist until P4**: control C
    and the `THEME_WET` shader are surfaces 11 and 12. This plan does not build P4 to answer it. See ruling R-9
    and Q2.

## Rulings on ambiguity (made in this plan; the lead may overturn any)

- **R-1. The stand-ins.** Each new family borrows a shipped family's GLBs, and takes its own tint by key (point 9):

  | Family | Stand-in GLBs | Why | Tint (spec 2.2, 4.2) |
  |---|---|---|---|
  | `oak` | `decor/cedar_{0,1,2}.glb` (5.4 / 4.4 / 3.3 m) | height-true to the oak's 5.0 / 4.2 / 3.4 m; the grove rule (0.6 a tile, no twin) is the cedar's own | foliage `scrub.1`, trunk `mud.2` |
  | `willow` | `decor/desert_tree_{0,1,2}.glb` (2.90 m) | an open, thin crown, lighter than the oak; short, and said so | foliage `fen.0`, trunk `mud.2` |
  | `shrub` | `decor/bush_{0,1,2}.glb` (0.90 m) | the lentisk's 1.0 m mound | foliage `scrub.1`, trunk `mud.2` |
  | `reed` | `decor/bush_{0,1,2}.glb` | nearest shipped height to a 1.0-1.5 m mat; a grass tuft at 0.40 m would read as bare marsh | foliage `dust.5`, trunk `scrub.1` |
  | `wet_grass` | `decor/grass_{0,1,2}.glb` | the same tuft; "lusher" is P3's geometry | foliage `grass.3` |

  Silhouettes are wrong by design: the capture judges TONE and PALETTE, and the PR says so. `shrub` and `reed`
  share URLs, so a wet map fetches the bush GLBs twice under two keys. That costs about 130 kB in P2 only, and it is
  recorded, not fixed.
- **R-2. The ground images.** `TERRAIN_GROUND_TEXTURE.wetland = 'green_basin_tile'` (a sward image; the ratio form
  recolours it to `fen.0`). `TERRAIN_SLOT_TEXTURES.wetland` names today's shared four. P3 replaces all five names,
  and adds their `GROUND_ALBEDOS` means, in the commit that ships the images.
- **R-3. `weather` is a seam, not a feature.** `TERRAIN_WEATHER` is total, `rain` for `wetland` only.
  `rendererOptionsFor` spreads `weather: 'rain'` only when it is `rain`. Nothing in P2 reads it. P4's `rainLight`
  is its first reader, and Task 1's light pin already has its `'clear'` arm.
- **R-4. `propMix` and the three prop kinds wait for P3.** A new `PropKind` needs a GLB, a `PROP_TRI_CAPS` entry
  on both sides and a mesh-catalogue file, and there is no honest stand-in for a bale. A wet map uses the global
  mixes in P2.
- **R-5. The remap is a rename at the push site.** Every roll, jitter, scale and variant is computed from the
  ORIGINAL family (`grass`, `bush`). Only the `family` field written into the placement is remapped. So a wet map's
  placements equal what the same input gives without the remap, family name aside. Task 6b pins exactly that.
- **R-6. `marshWater` takes the grid.** The spec's `marshWater(x, z)` must know where `~` is, so the shared function
  is `marshWaterAt(decor, width, height, x, z): number`, a water weight in 0..1 (water where it is >= 0.5). It is
  built from `terrain/noise.ts`'s hand-rolled `fbm2`: meanders as a thin band around an fBm isoline, pools as a
  second field over a threshold. Water is kept at least 0.25 tile inside the marsh boundary, so it never laps a
  causeway, a bank or a road tile. It is in `terrain/shared.ts` if `noise.ts` stays three-free (true at
  `93eb0d09`: it imports only `tile-hash`). P4's control-C bake samples the same function.
- **R-7. Reed clumps.** A `~` tile places 1 clump, plus 1 more when `tileHash` on its own stream is below 0.5
  (mean 1.5). Each clump tries up to 4 jittered centres, on four own streams, and takes the first that is not
  water. If all four are water, the clump is dropped. The scale roll is the per-tile 0.8-1.2. The footprint (about
  0.8 tile) is P3's, tuned with the real mesh.
- **R-8. The waterside pass** is pass 3 (the fourth). It acts on a plain open tile (`familyFor` gives `open`) that
  `isOpenScatterAt` allows and that is within Chebyshev `reach` (1) of a `~` tile. It rolls `waterside.p` (0.12) on
  a fresh offset pair, grepped unused in `decor-place.ts`, `prop-place.ts` and `scatter.ts` (7919/3571 is taken).
  The scale is 0.85-1.15, the open-tree range. **A tile where pass 2 rolled a tree is skipped**: pass 2's tree-band
  test is extracted as a pure helper that both passes call, so there are never two trunks on one tile.
- **R-9. The puddle-reflectance A/B moves to P4** (Q2). P2's capture shows the `mud.1` road, the `mud.3` marsh
  floor and the `fen.0` verge the puddles will sit on, with a KDF vehicle beside the track. The A/B (0.20-0.25
  against 0.35, and KDF-on-water) is P4's first capture, once the puddle term exists.
- **R-10. The `~` restriction is a data-gate rule.** `parseMap` stays theme-agnostic, as it is for `b` and `d`, so
  unit fixtures can use `~` freely. `validate_data.mjs` refuses `~` on a map whose `terrain` is not `wetland`,
  reading `THEME_SYMBOLS`' twin literal, which `terrain_symbols.test.ts` holds to `map.ts`.
- **R-11. `tileSurface` gives the marsh `scrub` at the cover-1 strength** (`SCRUB_TIER_STRENGTH[0]`, 0.4).
  `groundTone` gives it `quantise(composite(background, tones.marsh, 1))` when `tones.marsh` is set, and the open
  wash otherwise, so a theme without the field is byte-identical.
- **R-12. The greybox is Ein Qasab at spec 5.3's bands and markers**, authored by hand:
  - the west ridge with crags, copses and a boulder skirt;
  - the valley floor marsh (about 300 `~`) with two level-1 `r` causeways at y 12 and y 34;
  - the east downs with a 2-level crest and the hamlet on a knoll.

  Every building stands on one level, and every open step is at most 1 level a tile. One rule is added for the
  capture: **the west track runs past `kdf_start` (4, 44)**, so the sandbox force stands on a verge. The causeway
  doctrine pin, `jebel_matar` and the distinctness and visibility reports are P5.
- **R-13. The P2 light is `day`.** `rainLight` is P4, so the capture is the theme's tones under today's sun, with
  the `overcast.1` haze key and `hazeFar` 0.12. The capture sheet states this on every frame. Rain dims open-ground
  irradiance by 23% (spec 4.5), so the lead reads hue and palette, not final value.
