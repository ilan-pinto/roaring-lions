## 0. Three facts that shape everything below

- **A faction belongs to a seat, not to a side** (§2.2).
  - The host picks `mirror`, `kdf` or `sarim` (`packages/net/src/config.ts`: `Matchup`,
    `factionsOfMatchup`). Today a host who picks Sarim plays Sarim on **side 0**.
  - Every F-plan, by contrast, reads side 0 as "the player" and side 1 as "the authored enemy".
  - LD1 (ruled 16 Oct) narrows that: KDF is always side 0 in a faction matchup, so only side 1's
    human paths are new.
- **Lane C's order is now F1 → F3 → F2 → N2 → F4 → vehicle spacing**, with one sim plan in flight.
  - This order is from N2's own plan ("Sequencing"). It supersedes L5 and the stage-4 calendar.
  - F4 was written before N2 existed, and nothing in it mentions `Command`s or seats.
- **Neither KDF-v-Sarim map has a tunnel or a camp.** The two maps are `FACTION_MATCHUP_MAPS` =
  `tel_marum` and `wadi_tarfan`. Both carry zero `tunnels`, and no map has ever carried a camp tile.
  - `wadi_tarfan` already names the zones a versus rules file would use: `camp_0`/`camp_1`, three
    fords, two bluffs and two farms per side.

## 5. F4 asks (LD6): the per-side keys and `Command` fields

For Lane C's F4 controller, before `feat/gf4-production` is cut. **LD6, ruled 16 Oct (lead), as
recommended:** F4 keys its production API by side and lands its new verbs as `Command`s, with the
net whitelist in the same PR. Source: §1's gap rows 1, 2, 6–11, 14
and 18. The same memo is `_coord/f4-per-side-asks.md`.

**What F4 builds on (F2, then N2, land first):**
- F2: `purse = Int32Array(2)` in 1/2400ths (`PURSE_UNITS`), `logisticsOf(side)`; side 1's purse is
  hashed (C-R3, C-R18); the base rate accrues to side 0 only (C-R17).
- N2 Task 4: `{ kind: 'build', side, unit }` is set aside by `queueCommand`, drained in queue order by
  `MissionRuntime.applyQueued()` **before** `sim.tick()`, and discarded if no runtime took it (R-3).
  `applyQueued` skips `side !== 0` (C-R3); `validateCommand` drops `build`/`support` in versus. `canBuild`
  is the click-time pre-check (D3). `COMMAND_KINDS`, `cleanCommand` and `validateCommand` change in the
  same commit as the union.
- **F4's three new kinds sit beside `build`, not around it.** `RuntimeCommand` becomes
  `Extract<Command, { kind: 'build' | 'support' | 'cancelBuild' | 'setRally' | 'clearRally' }>`,
  `queueCommand` sets all five aside, and the one `applyQueued` drains them in queue order with the
  same `side !== 0` skip. A cancel and a build in one frame therefore run in the order they were sent.

**The rule for every ask: F4 builds the per-side shape; it does not open side 1 to a human.**
`applyQueued` keeps its `side !== 0` skip, and `validateCommand` keeps the versus drop for every
runtime kind. N3 lifts both in one commit, with its two-seat test. In F4, side 1 is reached only by a
direct call (sim tests) and by the AI spender, never by the wire.

### The asks (10)

1. **`requestBuild`.** `requestBuild(unitId, line?, side: 0 | 1 = 0)` and `canBuild(unitId, line?, side = 0)`.
   - `line` indexes `productionLines(side)`; omitted = D6's shortest queue on that side.
   - The trailing default keeps every side-0 caller unchanged: the dock, the five building plans and `boughtProbe`.
   - `Command`: N2's `build` gains `line?: number`, a plain int (a line index, not tiles).
   - `cleanCommand`: `line` is absent, or an int `0 <= line < MAX_LINES`.
   - `validateCommand`: unchanged from N2 (`!world.versus && cmd.side === side`). The runtime refuses a
     line that is out of range for `side`, because net cannot see lines.
2. **Spend and refund.** One private `spend(side, item)` / `refund(side, item)` on `purse[side]`
   (`cost * PURSE_UNITS`). Every path uses it: the human build, cancel, D4's camp-death refund and Task 9's `spendDown`.
   - Intel stays side 0's (F1's single `intelValue`), so a side-1 item with `intel > 0` is refused.
3. **The pop-cap refusal and its reservation.** These take a side: `firstRefusal(unitId, side)`,
   `buildBlockedReason(unitId, side = 0)`, `popCapped(unitId, side = 0)` and `populationView(side = 0)`.
   - The camp clause is per side. Side 0 keeps the `player_start` fallback (D2). A side 1 with no
     side-1 camp is refused and never falls back to `player_start`.
   - `population(side)` adds the queued and in-progress items of `productionLines(side)`: Task 3's
     "one reservation pool per side". This replaces F3's side-0-only `buildQueue` loop (F3 D2). No command.
4. **`cancelBuild`.** `cancelBuild(line, index, side = 0)`, where `index` -1 is the item in progress (Task 2's `cancel`).
   - `Command`: `{ kind: 'cancelBuild', side: number, line: number, index: number }`, all plain ints.
     `cleanCommand`: `line` as in ask 1, and `index` an int `>= -1`, under a bound.
   - `validateCommand`: `!world.versus && cmd.side === side`. The runtime refuses an unknown line or index.
5. **`setRally` / `clearRally`.** `setRally(line, x, y, side = 0)` and `clearRally(line, side = 0)`, plus a
   `canSetRally(line, x, y, side = 0)` pre-check (N2's D3 pattern: the dock's deny cue needs an answer at click time).
